CLAUDE.md と領域別 SOT の階層

CLAUDE.md はこのハーネスの最上位方針であり入口。言語／プロジェクト構造／運用原則／委任ルール／品質プロトコル／メモリ統合／ツール利用／ワークフロー習慣／タスク管理／パス限定ルール／画像生成／ユーザー向け資料という章立てで、Claudeの振る舞いの大枠を規定している。2026-07-22には「§1.10 Critical Partnership（依頼を仮説として扱い、根拠付きで反対する）」が加わり、2026-07-25には後述する外部モデルFableの審査席からの離脱を含む整理が入っている。

ただし領域ごとの詳細仕様は個別のSOT（正本）へ委譲されている。外部モデルへのルーティングは .claude/skills/relay/SKILL.md、セッションの永続化ルーティングは .claude/rules/session-persistence.md、agentのモデル階層(tier)はそのagent自身のfrontmatter、Authority Co-Reviewの発動条件は quality-loop/SKILL.md、外部モデルのエイリアス表は .claude/clover/models.jsonが、それぞれ正本。本資料と実際の正本群が食い違う場合は、CLAUDE.mdだけでなく該当する領域別SOTを優先して確認・修正すること。

モデル階層（tier）ポリシー

作業は具体的なモデル名ではなくtier（frontier / heavy / standard / light）で振り分けられ、各tierがエイリアス（opus / sonnet / haiku）に解決される。これがCLAUDE.md §2 Model Tier Policyの一元管理の要点で、モデルのバージョンが上がったときは、下の表を含めてどこも書き換える必要がない設計になっている。表そのものを書き換えるのは、tierの担当や振り分け方針が変わる時だけ。

CLAUDE.md §2 Model Tier Policy（現行）
tier解決先重み用途担当エージェント
frontier (authority)opus（役割スロット・注参照）最上位quality-loopの審査・最終品質判断・重要なアーキテクチャ判断（dispatchの慣習として決まる。特定のagentに固定されない）
heavyopus高計画立案・設計/アーキテクチャ判断・コード/セキュリティ/アーキテクチャレビュー・複雑なデバッグplanner, reviewer
standardsonnet中実装・通常のデバッグ・検証・資料/HTML作成executor, debugger, verifier, document-author
lighthaiku低探索・ファイル検索・簡単な確認explorer

debugger は既定で standard として動き、根本原因の特定が本当に難しい場合だけ一時的に heavy へエスカレーションする（そのエスカレーション自体が「複雑なデバッグ→heavy」の担い手になる）。

注：frontier authorityの規約と、外部モデルFableの扱い

frontierは固定のモデル名ではなく「役割スロット」。現在はopusに解決されており、レビューがopusを下回ることは規約上ずっと禁止——これは会話セッション自身がどのモデルで動いていても関係ない。

審査パネルは「frontier authority（仕様に合っているかを見る役）＋同tierのred-teamセカンドシート（反証・粗探しをする役）」を標準構成とし、relayがONかつ実際に中継経由で動いており既定の外部エイリアスがmodels.jsonにある、という条件（Authority Co-Reviewの発動条件）を満たした時だけ、既定の外部モデル（執筆時点2026-07-30はgpt-5.6-sol。最新の一覧は.claude/clover/models.jsonを参照）が3人目として加わる。

外部モデルFableは2026-07-25にこの審査席から外れており、現在の設計は特定の外部モデルの存在を前提にしていない。詳細はquality-loop/SKILL.mdのAuthority Co-Review節が正本。

reasoning深さ（effort）はtierとは独立の軸: planner / reviewer は effort: max をfrontmatterで固定しており（validate.mjsが未設定をFAILにする）、設計判断と最終品質ゲートは常に最大深さで考える。他のagentはセッションの/effort設定を継承する。

境界線（4つの分離）

このハーネスは4つの境界線で責務を分けている。

意思決定 と 実装 の分離

方針を決めるのは planner（heavy tier）、実際にコードを書くのは executor（standard tier）。harness skillの指揮者（conductor）自身はコードを直接触らず、委任と統合に徹する（harness SKILL.md Conductor Role）。

実装 と 品質判定 の分離

成果物を作る人（worker）と、それを審査する人（authority）は必ず別インスタンス。CLAUDE.md §1.3「Writer/Reviewer Separation」の実装形が quality-loop skill。審査は下限opus（frontier tier）で行われ、自分の成果物を自分で承認することはない。

製品コード と ハーネス本体 の分離

dev/{name}/ 配下が実際の製品コード、.claude/ 配下がその製品を作るための運用システム自身。check skillはこの2つを自動判別し、製品コードには build/type/lint/test の検証を、ハーネス本体には validate.mjsによる整合性スキャンを充てる。

セッション内の会話 と 永続化された記録 の分離

会話は消えても、tasks/todo.md / tasks/lessons.md / tasks/session-state.md、大規模実装中はオンデマンド作成の tasks/roadmap.mdも（dev modeではdev/{name}/tasks/）残る。ルーティングと書式の正本は .claude/rules/session-persistence.md。

全体構成図

読み方のポイント

指揮者（conductor）＝メインセッション自身が「委任・調整・判断」に徹し、実際のコード読み書き・実装・デバッグをsubagent経由で行うのは、harness skill使用時のConductor Roleとしてのルール（harness SKILL.md Conductor Role。背景としてCLAUDE.md §2）。harness workflowの外でも、コードの非自明な変更は必ずagentへ委任し（§2）、指揮者が直接手を動かせるのは単一点の設定/ドキュメント編集や1-2行の自明な非コード修正、相談などに限られる（CLAUDE.md §2「Direct work」）。
