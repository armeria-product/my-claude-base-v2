2段階の品質ゲート

このハーネスの品質保証は、大きく2段階に分かれる。

  • quality-loop ―― 成果物を作る過程そのものに組み込まれた、worker / authority 分離の審査ループ。
  • check ―― 「終わりました」と報告する直前に必ず通す、独立した最終ゲート。

quality-loop は「作りながら質を上げる」役割、check は「本当に完了と言えるか」を出口で確認する役割、という位置づけ。

quality-loop — Writer/Reviewer Separation の実装

CLAUDE.md §1.3「Never approve your own code」の運用形。原則は単純で、成果物を作った人は、それを自分で承認してはならない。

Loop Contract（最大3サイクル）
ステップ内容
1. Worker成果物を作る（既存の成果物を入力にすることもある）
2. Authoritynative Opus（既定）またはCLAUDE.md §1.11のゲートがONの間の明示Fableが独立コンテキストで審査。verdict は APPROVE / REQUEST_CHANGES。worker の弁明は見えない。コード成果物は使い捨ての worktree を使い、敵対的変異検証（あえて壊してみるテスト）も行う
3. 差し戻しREQUEST_CHANGES なら、指摘全文＋「指摘箇所のみ修正・範囲拡大禁止」の制約とともに worker へ
4. 再審査CRITICAL/HIGH は必ず修正。MEDIUM/LOW は worker の裁量（却下理由を記録）。テストや判定ロジックに触れた修正は、壊す→RED確認→戻す→PASS確認という変異検証の証拠が要る。3サイクル目でも未APPROVEならユーザーへエスカレーション
5. VerifierAPPROVE 後、証拠ベースの最終検証（テスト・diff・ログ）を実行

計画・設計・アーキテクチャの審査（planner self-review・reviewer target:architecture）と、通常のコードレビュー（reviewer target:code）は、サイクル1に限り2席の常設審査体制で動く ―― 仕様適合レビューと「赤チーム視点」（あら探し役、verdict は出さない）は通常Opus×2。.claude/.fable-statusがONのとき（CLAUDE.md §1.11）だけ、両席を明示Fableへ切り替えてFable×2として動かす。混在、無言の切替、sonnet/haiku/inherit/unknown/外部idへの降格は禁止。さらに (1) relay ゲートが ON、(2) このセッション自体が relay 経由で動いている、(3) models.json の先頭エイリアスが辞書に存在する、の3条件が揃うと、native Fableとは別の外部モデルが3人目の co-reviewer として加わる。サイクル2以降の再審査は同じauthority規約の単独席に戻る。どの構成でも最終的な APPROVE / REQUEST_CHANGES の判定権は常に frontier authority 側に残り、赤チーム席・外部 co-reviewer 席は判定を出さない。セキュリティレビュー（reviewer target:security）と verifier は対象外のまま。複数の審査結果は Fusion Composition の手順（reviewer target:fusion による統合 → fusion-detect.mjs による機械的な分岐判定 → 再照会は最大1回）で1つにまとめる。/improve の無人ループだけは、実行コストを一定に保つため co-review を行わず authority 単独で審査する。

なぜ自分でレビューできないのか

Writer/Reviewer Separation の根拠はシンプル。自分が書いたものを自分で審査すると、見落としを見落としたまま承認してしまう構造的なリスクがある。だから常に別インスタンス・独立コンテキストの authority を立てる、というのがこのハーネスの一貫した設計判断（例外は1〜2行の自明な修正のみ）。writerとauthorityがともにOpus（§1.11ゲートON時はともにFable）でも自己承認は不可。「別モデル」まで保証されるのは、条件を満たして外部モデルが別のco-reviewer席として同席した場合だけ。

check skill — 完了報告前の単一入口

check は変更対象を自動判別し、適切な検証を実行する。

check skill の対象判定と実行内容
変更対象実行する検証
ハーネス本体（.claude/・CLAUDE.md・README.md）node .claude/scripts/validate.mjs による整合性スキャン
製品コード（dev/** 等）verifier agent の6フェーズ（下記）
UI変更を含む場合上記に加え、/preview（起動→スクリーンショット→コンソール確認）
HTML資料（doc skill / §10成果物）自己完結性lint（下記参照）

1〜2行の自明な修正や、ハーネスに影響しない純粋な docs のみはスキップ可能だが、それ以外は FAIL のまま「完了」を報告することはない。

verifier の検証パイプライン（6フェーズ）

「動くはず」ではなく、テスト出力・diff・ログ・grep結果のような証拠だけを根拠にする（CLAUDE.md §1.2）。

verifier agent の6フェーズ
フェーズ内容
1. Understand変更が何をすべきだったか、期待される挙動、失敗の見え方を確認する
2. Build / Type自動検出したツールでビルド・型チェックを実行。FAILならここで即座に報告し、残りのフェーズは行わない
3. Lintlinterを実行し所見を報告する（自動修正はしない）
4. Testテストスイートを実行し、成功/失敗/スキップ件数と失敗の詳細を報告する
5. Behavioral + Regression変更前後の挙動差を証拠として示し、関連機能への影響と、コード中に残ったconsole.log等のdebug artifactを確認する
6. Verdict + Diff Reviewgit diffで変更ファイルの意図を確認し、PASS / FAIL / INCOMPLETEを証拠つきで判定する

HTML資料の自己完結チェック

ユーザーが読むための資料（レポート・分析結果・ガイド等）は CLAUDE.md §10 に従い、外部依存ゼロの自己完結HTMLとして作る。check はこれを許可リスト方式で検証する。

禁止される外部参照

  • http:// / https:// を指す href / src / srcset
  • プロトコル相対の //host 参照
  • 外部の @import / CSS url(...)
  • 外部を指す <script src> / <link> / <iframe>
  • 外部Webフォント・CDN読み込み

許可されるもの

  • インラインの <style> / <script>（src属性がないもの）
  • data: URIによる画像埋め込み
  • インラインSVG（xmlns="http://…"のような名前空間宣言は取得ではないため対象外）
  • 同一文書内フラグメント（href="#toc"等）
複数ページのガイドでの相対リンク

この lint が主眼に置くのは、スタイルシート・スクリプト・画像のような「そのページ自身の描画に要るリソース」が外へ抜けていないかで、単体でコピー・添付しても壊れない、という §10 の1ファイル完結の保証を守るためのもの。ただし check skill 自身の実行規則は、同一文書内フラグメント以外の相対パスやremote参照は1件でもあればFAILと明記しており、字面どおりに読めば本ガイドのように同じフォルダ内の複数ページを行き来する<a href="index.html">のようなナビゲーションリンクも対象に含まれてしまう。つまりこれは解釈の幅の問題ではなく、正本どうしが実際に矛盾している状態 ―― check skill の文字どおりの規則と、本ガイド自身が採用した相対ナビゲーション ―― であり、どちらを優先するかはユーザーの裁定を仰ぐまで未確定として扱う。

PASS / FAIL 判定表

自己完結lintの判定基準
検出内容判定
remote参照（http(s):// または //host）が1件でもあるFAIL
外部CDN・外部Webフォントの読み込みがあるFAIL
インラインの<script>のみでsrc属性なしPASS
すべての参照が同一文書内フラグメント・data:・インラインSVGPASS
<code>/<pre>内にURL文字列が引用として書かれているだけPASS（引用は対象外）
通常のHTMLで、同一文書内フラグメント以外の相対パス参照（他ファイルへのhref等）があるFAIL
梱包済みスライド（*.deck.html）内の <script src="<uuid>"> 等、同梱資源への参照PASS（.deck.html限定の例外。remote参照だけがFAIL）

FAILが1件でもあれば、document-authorへ差し戻して修正 → 再検証、という流れ。この資料セット自身の自己監査結果: 本文中のコマンド例のURLはすべて<code>内の引用。実際のリンクは、大半が同じフォルダ内の相対パス（index.html等への行き来）だが、index.htmlからdocs/直下のsettings-reference.html・weasyprint-setup.htmlへ1階層上がる相対リンクが2件ある ―― これも上表の「通常のHTMLでの相対パス参照」に該当し、前段のコールアウトで触れた正本どうしの矛盾がそのまま当てはまる。
