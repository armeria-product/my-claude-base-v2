変更するとき、どこを見るか

skill・agent・hook・rule・script・製品コード・ユーザー向け資料 ―― それぞれを変更するときに確認すべき正本と、validate.mjs が機械的に守っている整合性をまとめた早見表。

対象 .claude 配下の変更全般 正本 CLAUDE.md ほか各ファイル 最終確認 2026-07-30 現状の repo で裏取り済み

新しい skill を追加するとき

  • まず既存の .claude/skills/*/SKILL.md を1つ読み、frontmatter（name / description / user-invocable）と本文構成を踏襲する。
  • description は「どんな時に自動発動するか」の判断材料になる。「〜して」の形で具体的なトリガー語（呼び出し文言）を日本語で書く。
  • 既存 skill と役割が重複していないか確認する。軽い処理は skill のまま、独立した文脈が要る処理は agent へ、というのが CLAUDE.md §5.3 の解決順（skill → agent → command）。
  • 本文中で agent を呼ぶ記述をするときは、モデル名を直接書かない。「Skills, commands, and docs は具体的な Claude のモデル ID を書いてはいけない」（CLAUDE.md §2）。この禁止は Claude 側のモデル名だけが対象で、外部モデルの alias 辞書である .claude/clover/models.json はこの禁止の対象外。
  • 作成後は node .claude/scripts/validate.mjs を実行し PASS を確認する。skill については「SKILL.md の frontmatter name: がディレクトリ名と一致しているか」「本文中の subagent_type: が実在する agent 名を指しているか」も機械的に検査される。

agent を追加・変更するとき

正本は .claude/rules/agents.md。変更時は次を必ず守る。

  • frontmatter の形式（model / description / tools / 必要なら effort）を既存 agent と揃える。
  • model: は tier alias（opus / sonnet / haiku / inherit）、または clover の外部モデル id（claude-<alias>。<alias> は .claude/clover/models.json に実在するもの）のみを書く。実在の Claude モデル ID を直接固定するのは禁止 ―― バージョンが上がるたびに書き換えが要る壊れ方をするため。
  • clover のモデル id を書いた agent は、clover 経由で起動したセッションでしか動かない。特定の呼び出しだけ一時的に外部モデルへ振りたい場合は、frontmatter 固定よりも relay skill の RELAY-MODEL: マーカー（呼び出しごとに指定）の方が、素の起動でも壊れず可搬性が高い。
  • 読み取り専用の agent（reviewer / verifier / explorer）には、Write / Edit / NotebookEdit のような書き込み系ツールを一切持たせない。
  • 読み取り専用 agent の Bash は「読み取り・テスト実行専用」に限定する。唯一の例外は reviewer の敵対的変異検証（adversarial mutation probe）で、明示的に許可された使い捨ての worktree の中でだけ書き込みが許される（本体のツリーには触れない）。
  • planner と reviewer は effort: max の frontmatter 固定が必須。欠けていると validate.mjs が FAIL にする。
  • agent 定義の変更は全プロジェクトの挙動に影響するため、変更範囲をユーザーに確認してから進める。
  • 変更後は簡単なタスクで実際に動かし、壊れていないことを確かめる。

validate.mjs が守っている整合性

node .claude/scripts/validate.mjs はハーネス本体（agent / skill / rule / hook / CLAUDE.md 自身など）の整合性を機械的に検査する、ハーネス変更の最終チェックポイント。check skill は変更対象が .claude/ 配下や CLAUDE.md / README.md のときに、これを自動で選ぶ。

validate.mjs の主なチェック（現行11項目）
チェック内容検出時
agent の frontmatter（tier alias / clover id の妥当性、読み取り専用 agent への書き込みツール混入、planner・reviewer の effort: max 欠落）FAIL
skill の frontmatter（name: とディレクトリ名の一致、description 必須、subagent_type: が実在 agent を参照しているか）FAIL
hooks 登録 ―― settings.json に書かれた hook ファイルの実在確認。block-*.js のような安全装置が未登録のときFAIL
hooks 登録 ―― block-*.js 以外の hook ファイルが settings.json に未登録のときWARN

廃止済み名称の死んだ参照（code-reviewer / plan-lite・full / .codex/ / CLAUDE_JP / addons / 「frontier dispatch override」旧称 等が CLAUDE.md・README.md・.claude 配下に残っていないか）FAIL
rules の frontmatter（paths: が空でなく存在するか。空だと発火しないルールになる）FAIL
不変文言（invariant canary）の照合 ―― 「never fall below opus」「Critical Partnership」等、規約の根拠になる特定の文言が該当ファイルから消えていないかを直接照合FAIL
機密ファイルの deny-list 整合 ―― settings.json の permissions.deny と block-secret-read.js のパターンが対応しているかWARN
relay の alias 辞書ポインタ ―― relay/SKILL.md が models.json を正本として指し続けているかWARN
Windows パス / エンコーディング（POSIX固定パスの残存、PowerShell 呼び出しでの OutputEncoding 欠如）／ tasks/lessons.md のサイズ（18KB 超）WARN
FAIL と WARN の違い

FAIL は「壊れている、または安全上見過ごせない」ものとして扱われ、check skill が完了報告をブロックする根拠になる。WARN は「気づいてほしいが即ブロックはしない」もので、報告の際に件数だけ確認すればよい。

製品コード（dev/ 配下）を扱うとき

  • 新しい製品なら dev/{product-name}/ を作り、その製品専用の tasks/todo.md / tasks/lessons.md を持たせる（正本: .claude/rules/dev-projects.md）。
  • 要件が曖昧な新規ビルドは、実装前に4項目（目的・利用者と困りごと／必須機能と範囲／見た目・UX／技術的な制約と完了条件）を確認してから着手する。
  • 非自明な変更は writer と reviewer を分け、quality-loop の Loop Contract（worker が作り、frontier tier が審査、max 3 サイクル、最後に verifier が証拠ベースで検証）を通す。
  • UI を含む変更は check skill が /preview（起動 → スクリーンショット → コンソール確認）まで自動で回す。
  • 製品らしい規模の新規依頼（新製品や、ユーザーが既存製品と比較するような大きな新機能）には、着手前に類似製品の調査と先回りのギャップ提案が期待される（CLAUDE.md §1.10 Critical Partnership）。反対するときは根拠と代替案をセットで示し、最終判断はユーザーに委ね、押し切られた場合は成果物の「Objections & Rulings」に記録する。

ユーザー向け資料（HTML）を扱うとき

  • 正本は CLAUDE.md §10 と .claude/skills/doc/SKILL.md。ユーザーが読むための報告書・調査結果・ガイド等は自己完結 HTML、tasks/ や plans/ のような内部作業ファイルは Markdown のまま、という線引きを守る。
  • 起点は .claude/skills/doc/template/doc.template.html。作成そのものは document-author agent に委任するのが基本。
  • スライド・プレゼン資料は deck モード（1920×1080 の <section> を並べる自己完結 .deck.html）で作る。編集可能な PPTX への変換は要求時のみ node .claude/scripts/html2pptx.mjs が行い、これは失敗を隠さない（fails loud）。PDF 変換の html2pdf.mjs が失敗時に HTML のまま進める（fails open）のとは逆で、PPTX そのものが依頼された成果物のため。
  • 作成後は check skill の自己完結チェック（外部参照ゼロのチェック）を必ず独立に通す。

基本チェックリスト（変更全般）

  • 変更が CLAUDE.md の既存規定と矛盾していないか確認した
  • モデル名を直接 pin せず、tier alias または agent の frontmatter に委ねた
  • 非自明な変更は、成果物を作った本人以外がレビューする体制（quality-loop）を通した
  • ハーネス本体を変更した場合、node .claude/scripts/validate.mjs が PASS することを確認した
  • 製品コードを変更した場合、check skill（verifier の6フェーズ、UI なら /preview も）を通した
  • 5ファイル以上に影響する変更、またはセキュリティ関連の変更は、事前にユーザーへ範囲を確認した
  • 想定外の挙動やユーザーからの訂正があれば、tasks/lessons.md に記録した
迷ったときの原則

同じやり方で3回失敗したら、角度を変えて考え直す（§1.5）。「たぶん動く」は禁句 ―― テスト出力・diff・ログ・grep 結果のような証拠なしに「完了」とは言わない（§1.2）。

正本のズレに注意

このページを含め、ドキュメント側の記述は古くなりやすい。数字（agent 数・skill 数・hook 数など）や引用文は、書く前に必ず repo の現物（.claude/agents/・.claude/skills/・.claude/settings.json 等）を直接確認してから書く。
