開発ライフサイクル / 実行フロー

1つの依頼が「計画 → 実装 → レビュー → 検証 → コミット/PR → 記録」までどう流れるか、各skillがどこでつながっているかを追う。

対象 plan / harness / quality-loop / check / doc skill 更新 2026-08-12 最新化済み

plan skill — light / heavy の分岐

plan skillは、実装に入る前に必ず最初に複雑度を判定する（Step 0 — Complexity Gate）。判定は自動で、下の4シグナルを見て、1つでもheavy寄りが当てはまればheavy path、すべてlight寄りならlight pathに進む。判定が割れて自動で決めきれない場合だけ、ユーザーに1問だけ確認する。

Step 0 Complexity Gate（4シグナル）
シグナルlight寄りheavy寄り
影響ファイル数1〜23以上、または複数モジュール横断
変更の性質局所的な修正・小機能新機能・アーキテクチャ判断
リスク低い認証/決済/データ移行/外部公開
要件の明確さ確定している調査しないと決められない

light path（軽量パス）

曖昧な依頼を実装可能な仕様に変換するだけのモード（この段階では実装しない）。4つの観点（Goal 40% / Constraints 20% / Success Criteria 25% / Context 15%、既存プロジェクトの場合はContextの重みを25%に引き上げ）で曖昧さをスコアリングし、1ラウンド1質問・最大5ラウンドのインタビューで詰める。ラウンド3以降は「本当に必要か」「MVPまで削るなら何を残すか」「境界値はどうなるか」を問うChallenge Modeが加わり、根拠のある反論はどのラウンドでも即座に行う義務がある（CLAUDE.md §1.10 Objection duty）。曖昧度が20%以下、または5ラウンドに達したら要件サマリを出力して終了する。実装する場合はこのサマリを入力に/harness等を使うか、作業中に規模が大きいと判明した時点でheavy pathへ引き上げる。

heavy path（重量パス）

Research → GO/NO-GOゲート → Plan → Implement の4段階。各段階の成果物が次段階の入力になる。

  1. Phase 1: Research — 4系統の調査を並列で行い research.md を出力する: (1)要件整理（planner、light path成果物があればスキップ）(2)コードベース影響調査（explorer）(3)必要なら外部調査（指揮者がWebSearch/WebFetch）(4)ドメインリサーチ（指揮者、product-shaped＝新規プロダクトやユーザーが既存製品と比べる大きな機能の場合のみ）— 競合3〜5個の必須機能・よくある不満点を調べ、テーブルステークス（当然備えるべき機能）のギャップ提案を先回りで用意する。
  2. GO/NO-GO ゲート — 「要件は明確か」「前提は検証済みか」「コードベース影響は把握できているか」「進行を止めるリスクはないか」「複雑度は許容範囲か」に加え、「ギャップ提案・反対意見はユーザーに提示し裁定を得たか」を含む6項目を判定し、GO / NO-GO / NEEDS-CLARIFICATIONを判断する。ギャップ提案と反対意見は1回にまとめたAskUserQuestionで裁定し、裁定内容はresearch.mdへその場で追記、GO後にPLAN.mdの台帳へも転記する。
  3. Phase 2: Plan — planner が計画を作り（必要なら任意のPropose層で複数executorの叩き台をplannerが統合）、別インスタンスのplannerがSelf-Review Modeで審査する。通常は仕様適合席と赤チーム席をOpus×2で起動し、.claude/.fable-statusがONのとき（CLAUDE.md §1.11）だけ両席を明示Fableへ切り替えてFable×2として動かす。混在や下位モデルへの降格は禁止。条件を満たせば、native Fableとは別の外部モデルが3人目としてさらに加わる（詳細は architecture.html のモデル階層ポリシー節を参照）。APPROVEまで最大2回修正し、PLAN.md を出力する。
  4. Phase 3: Implement — ここから先はharness skillのパイプラインを実行エンジンとして使う。feature / bugfix / refactorのいずれかのワークフロータイプを選び、各フェーズにテストゲートを設ける。全フェーズ完了後、reviewer（code、全差分レビュー）→ 対応 → verifier（最終E2E検証）で締める。

harness skill — 実装パイプライン本体

複数の専門agentを束ねてタスクを端から端まで遂行する、実行エンジンとしてのワークフロー。5種類のワークフロータイプがある。

harness のワークフロータイプ
タイプ用途主な流れ
feature（既定）新機能実装planner → planner self-review → （product-shapedなギャップ提案/反対意見の裁定）→ executor → reviewer(code) → verifier
bugfixバグ修正再現ゲート → debugger（根本原因特定、不明な場合は仮説を最大3つまで並列で切り分け）→ fix/verifyループ（最大3サイクル）→ 回帰テスト → 収束/エスカレーション（1回）
refactor安全なコード再構成reviewer(architecture) → executor → verifier（挙動不変の確認）→ reviewer(code)
securityセキュリティ集中レビューreviewer(security) と reviewer(code) を並列実行 → verifier
research実装前調査explorer（並列調査）→ reviewer(architecture)（方向性提案）

指揮者（conductor）はここでも「委任・調整・集約・報告」のみを担当し、コードのRead/Edit/Writeは行わない。依存のないステップは並列実行される（例: bugfixの仮説fan-out）。

quality-loop skill — 品質ゲートの共通部品

harness / plan から呼ばれる共通プリミティブ。成果物を作る側（worker）と審査する側（authority）を必ず別インスタンス・独立コンテキストに分離し、APPROVEになるまで送り返す（最大3サイクル）。通常の権威モデルはnative Opusで、CLAUDE.md §1.11のゲートがONの間だけ明示Fableへ切り替える。同じモデル同士でも自己承認は不可。モデルそのものが変わる独立性は、条件を満たして別の外部モデルが審査に加わったときに限られる。tier・審査パネルの詳細構成は architecture.html のモデル階層ポリシー節を参照。

  1. Worker が成果物を作る
  2. Authority が審査 — APPROVE / REQUEST_CHANGES。許可集合はnative fable | opusだけ（Opus既定、§1.11ゲートON時のみ明示Fable）で、workerの弁明は見えない独立コンテキスト。
  3. REQUEST_CHANGES なら差し戻し — CRITICAL/HIGHは必修正、MEDIUM/LOWはworkerの裁量（却下理由を記録）。
  4. 再審査 — 3サイクル目でもAPPROVEでなければ、ユーザーにエスカレーション。
  5. APPROVEなら verifier が最終の実証的検証

コミット / PR — もう一つの記録のかたち

このリポジトリはブランチベースの運用で、変更がmainに直接乗ることは一度もない。mainが動くのは、ユーザーがPull Request（取り込み提案）をGitHub上でMergeした時だけ。block-direct-to-main.jsフックが、main/masterを対象にしたgit commit/git pushをその場で止める。

  1. 作業ブランチを1本作る — 最新のmainから<topic>-<YYYY-MM-DD>という名前で分岐する（例: workbench-review-2026-07-05）。すでに作業中のブランチにいるなら、それをそのまま使い続ける。
  2. コミット → プッシュ → PR — 作業ブランチにコミットし、プッシュし、その作業ブランチからmainへのPull Requestが存在することを確認する（なければ作成、あれば新しいコミットが自然に積み上がる）。1つの作業ブランチにつきPRは1つ。
  3. mainを動かすのはユーザー自身 — Claude側からmainへローカルでコミット・プッシュ・早送りマージすることは一切しない。ユーザーがPRの中身をGitHub上でレビューし、良ければ「Merge」ボタンで反映する。

block-pr-without-todo.jsフックが、gh pr createの実行そのものにさらに3つの条件を課す。(1) 宛先ブランチの確認 — --baseがmain/master以外を指していると拒否する。宛先にした枝が先にマージされて消えると、中身がmainに届かないまま「マージ済み」に見えてしまうため。(2) todo.mdの更新確認 — このブランチのtasks/todo.mdが、ブランチを作った時点より後に更新されているか（更新日時だけを比較する簡易チェックで、内容の妥当性までは見ない）。(3) CODEMAP.mdの更新確認 — そのリポジトリにtasks/CODEMAP.mdがあるときだけ、todo.mdと同じ扱いで更新確認が入る（無いリポジトリは無影響）。構造を変えていなければ書き直す必要はなく、最終確認: YYYY-MM-DDの行を今日の日付にするだけでよい。ただしfile:lineの行番号そのものがずれた場合は、構造を変えていなくても注記の更新が要る — その食い違いはnode .claude/scripts/validate.mjsの節18が機械検査する。いずれもgh api経由の作成やGitHubのWeb画面からの作成、複数行にまたがるgh pr createコマンドまではカバーしていない。todo.md / CODEMAP.mdの更新確認は、コマンド中でpushdやPowerShellのSet-Locationのようなディレクトリ移動が使われると、以降どのリポジトリを見ればよいか追えなくなる（フックのヘッダコメントに明記された既知の対象外）。

重要な変更のコミットメッセージには、平易な日本語で次の構造化トレーラーを添える。

Commit Protocol の構造化トレーラー
キー書く内容
Constraintどんな制約がこのやり方を選ばせたか
Rejected検討して却下した代替案
Confidencehigh / medium / low
Not-tested検証していない範囲とその理由
結果を報告するときの言葉づかい

コミット/プッシュ/PRの結果を報告するときは、生のgit/GitHub用語を並べず、平易な日本語で「何が起きたか」「次にユーザーが何をすればよいか」を伝える（例: 「変更を〇〇ブランチに保存し、GitHubの取り込み提案（PR）を作成しました。中身を見て良ければ『Merge』ボタンでmainに反映できます」）。

doc skill / document-author — 資料作成フロー

ユーザーが読むための成果物（レポート・調査結果・ガイド等）を作るときの入口。document-author（standard tier）に委任し、自己完結HTMLの生成・自己検証・ブラウザ表示までを行わせる。生成後はcheck skillが独立に自己完結性を再検証する、二段構えのゲート。PDFは要求時にhtml2pdf.mjs（WeasyPrint、未導入でも失敗せずHTMLのまま残す）で、編集可能なPPTXはスライド用途で要求時にhtml2pptx.mjs（未導入だと明示的に失敗する）で、それぞれHTMLから派生生成する。

セッション永続化との関係

会話がコンパクトされても、あるいはセッションが切れても、進行中の状態はtasks/配下の4ファイル — todo.md / lessons.md / session-state.md、大規模実装中はオンデマンド作成のroadmap.md（dev modeではdev/{name}/tasks/）— に残る。ここには性質の違う2つの仕組みがあり、混同しないよう分けて説明する。(1) セッション開始のたびに画面へ表示する仕組み — session-start.jsフックが、4ファイルすべてをセッション開始時に読み込んで表示する。ただし表示には合計24KBの上限があり、超えた分は優先度の低いファイルから順に削られる（全文はファイル本体を直接読む）。加えて、同じくオンデマンド作成の5番目のtasksファイルCODEMAP.md（構造の地図、§6.5）がそのリポジトリに存在する場合は、この24KBの枠の外側に、ファイルパスと##見出しの一覧だけの短いポインタ block を必ず追記する ―― 本文は入れない。地図の中身を毎回読ませるのではなく、「地図がどこにあるか」だけを毎セッション安く知らせる設計。(2) /save-sessionが空ファイルを最初に作る仕組み（bootstrap、初回だけ雛形を用意する処理） — こちらはプロダクト文脈（dev mode）を検出したときだけ動き、session-state.md / todo.md / lessons.mdの3ファイルだけが対象で、roadmap.mdとCODEMAP.mdは対象外（どちらも必要になったタイミングで指揮者が作る、§6.4 / §6.5）。ルーティング先の判定・書式契約の正本は.claude/rules/session-persistence.md。plan（およびharnessが起動するplanner）は、この§6書式契約に従ってtodoやlessons、大規模実装時はroadmapにも書き込む。

一連の流れ図

同じ失敗を繰り返さない

quality-loopもharnessのbugfixループも、同一アプローチが改善しないまま3サイクル続いたら、そこで止めて角度を変える（CLAUDE.md §1.5）。ユーザーへの相談も、ここまでの状況を1回にまとめて行う（§6.2 Autonomous Bug Fixing）。
