llm-relay：バックエンド自動フェイルオーバー

主系(Claude)の異常時に、待たせず代替バックエンドへ無停止で切り替える仕組みを入れる。

概要

現状の llm-relay は主系が落ちると呼び出しがそのまま失敗し、Claude Code 側でリトライが詰まる。ここにヘルス判定つきのルーティング層を足して、主系の異常を検知したら副系へ自動で流す。副系は既存の GLM / Kimi / gpt-5.5(Codex OAuth) を再利用する。

  • 非停止 ― 呼び出し中の失敗を握って副系へ再送、呼び出し元にはエラーを見せない
  • 自動復帰 ― 主系が回復したら次のリクエストから自動で戻す
  • 可観測 ― どのバックエンドに流したかをログとヘッダで追える

現状と課題

いまの切り替えは環境変数の手動書き換え。障害のたびに気づいて直す必要があり、復帰も手作業。

課題影響優先度
主系ダウンの検知が手動気づくまで全リクエスト失敗高
切替が env の手書き復旧に数分のロス＋事故のもと中
どこに流れたか不可視後追い調査ができない低

設計方針

ヘルス判定の持ち方

「毎回叩いて確認」か「失敗したときだけ切替」かで、遅延と正確さが逆になる。

A案：常時ヘルスチェック
  • 別スレッドで定期 ping、状態を先に持つ
  • 切替が速く、初回リクエストも巻き込まない
  • ping コスト＋実装が増える
⇄
B案：失敗時のみ切替
  • 実リクエストの失敗を検知して副系へ再送
  • 実装が薄い・余計な通信ゼロ
  • 切替の当たり1発分は必ず遅延する
結論

まず B案（失敗時のみ）で入れる。→ 個人用途で ping を回し続けるコストが見合わない。連続失敗が閾値を超えたら一定時間だけ主系を「開いた」状態にして A案相当のショートカットを足す、という段階導入にする。

状態遷移

サーキットブレーカ的に closed → open → half-open の3状態で持つ。open の間は主系を飛ばして副系へ直行、一定時間後に half-open で1発だけ試す。

実装ステップ

  1. 状態機械を切り出すbackend ごとに closed/open/half-open を保持する router.ts を作る。判定ロジックはここに閉じ込める。
  2. server.ts を router 経由にする直接 backend を呼んでいる箇所を router.dispatch() に差し替え。呼び出し元の interface は変えない。
  3. 設定を外だしする閾値・冷却時間・副系の優先順位を relay.toml で持つ。下記のブロックを追加。
[failover]
# 連続失敗がこの回数を超えたら open にする
threshold = 3
# open のまま待つ秒数（この後 half-open）
cooldown_sec = 30
# 主系が落ちたときに上から順に試す
fallback = ["glm", "codex"]

ディスパッチ本体はこんな形。tryBackend が投げたら次の候補に落ちる。

async function dispatch(req: RelayRequest): Promise<RelayResponse> {
  const chain = [primary, ...fallbacks];
  let lastErr: unknown;

  for (const backend of chain) {
    if (breaker.isOpen(backend.id)) continue;   // open はスキップ
    try {
      const res = await backend.call(req);
      breaker.onSuccess(backend.id);
      res.headers["x-relay-backend"] = backend.id;
      return res;
    } catch (err) {
      breaker.onFailure(backend.id);             // 閾値超えで open
      lastErr = err;
    }
  }
  throw new AllBackendsFailedError(lastErr);      // 全滅時のみ表に出す
}

注意

副系ごとにツール呼び出しの対応度が違う。gpt-5.5(Codex OAuth) は確認済みだが、GLM 側の tool-use 挙動が主系と揃うかは未検証。フェイルオーバー先で挙動が変わると気づきにくいので、切替が起きたことをログで明示する。

冷却時間(cooldown_sec)を短くしすぎると、主系が不安定なとき open/half-open を往復して不安定さが増幅する。まず 30 秒で入れて様子見。

メモ

状態遷移は入れる前に単体で書けるので、server.ts に触る前に router.ts 単体でテストを通しておくと結合が楽になる。
